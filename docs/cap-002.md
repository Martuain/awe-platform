# CAP-002 — Website Strategy

## Objective

Transform approved Business Discovery context into a reviewable strategy for the website that follows.

## Contract

Input: approved CAP-001 `DiscoveryContext`.

Output: `WebsiteStrategy` containing sitemap, page objectives, content strategy, design direction, rationale and source context version.

## Lifecycle

`draft → ready_for_review → approved`

## API

- `POST /api/v1/website-strategy/generate?project_id={id}`
- `GET /api/v1/website-strategy/{project_id}`
- `POST /api/v1/website-strategy/{project_id}/approve`

## Principle

No strategy generation before Business Discovery approval.

## Vertical slice

The first implementation is deterministic and provider-independent. A real model adapter will be introduced behind the existing gateway after the capability contract and evaluation behavior are stable.

## Hardening cycle — 2026-08-20

The CAP-002 hardening cycle added the minimum controls required before freezing the capability:

- deterministic strategy evaluation;
- explicit evaluation dimensions: completeness, business alignment, traceability and actionability;
- approval is blocked when the strategy does not pass evaluation;
- revision endpoint with user feedback;
- deterministic application of supported natural-language revision feedback (positioning and primary CTA);
- backward-compatible explicit `CTA: ...` revision syntax;
- strategy version increments on revision;
- approved strategies are immutable;
- in-memory repository retains strategy versions instead of replacing the complete history;
- SQL persistence now maintains a current strategy record plus append-only strategy-version records;
- API integration test covers generate → evaluate → revise → approve → reject post-approval revision.

### Evaluation rule

The initial deterministic evaluator is intentionally a development baseline, not a substitute for semantic model evaluation. It verifies structural completeness and traceability and provides a repeatable contract that can later be complemented by model-based evaluation.

### Revision rule

A revision creates a new strategy version. It does not mutate the approved artifact. Supported feedback is applied to the new candidate before re-evaluation. CAP-002 therefore preserves the same human-alignment principle established by CAP-001:

```text
Draft / Ready for Review
        ↓
User feedback
        ↓
New version
        ↓
Evaluation
        ↓
Approval
```

### Validation

The CAP-002 strategy test suite now covers generation, explicit CTA revision, natural-language positioning + CTA revision, approval and post-approval immutability.

The full monorepo CI remains the authoritative validation gate.
