# CAP-003 Deployment Hardening — v0.1.1

## Trigger

GitHub CI passed for CAP-003, but the first Vercel production deployment exposed deployment-environment and dependency-security issues.

## Findings

1. Next.js 15.4.6 was flagged by Vercel as vulnerable.
2. ESLint's `eslint-config-next/core-web-vitals` import failed under Vercel's ESM module resolution because the `.js` extension was not resolved.
3. pnpm 10 ignored lifecycle/build scripts for `sharp` and `unrs-resolver`.
4. The repository was also on React 19.1.1. React's current security guidance shows later RSC fixes are required, so we will not knowingly retain that baseline.

## Decisions

### Next.js

Upgrade the Studio to Next.js 15.5.21, the patched 15.x Maintenance LTS target identified by the Next.js July 2026 security release. We deliberately stay on the 15.x line to avoid introducing a major-version migration while CAP-003 is being stabilized. Next.js currently lists 15.x as Maintenance LTS. 

### React

Upgrade React and React DOM to 19.1.9. React published a July 21, 2026 Server Functions security fix for the 19.1.x line at 19.1.9. This is the current patched 19.1.x target rather than the earlier 19.1.7 version. 

### ESLint

Use the explicit `eslint-config-next/core-web-vitals.js` import so Node's ESM resolution matches the deployed environment.

### pnpm build scripts

Explicitly allow only `sharp` and `unrs-resolver` to execute dependency build scripts using the root `pnpm.onlyBuiltDependencies` setting. We do not enable arbitrary dependency lifecycle scripts.

## Lockfile rule

The lockfile must be regenerated by pnpm after these manifest changes. It must **not** be manually edited.

Run from the repository root:

```bash
pnpm install
```

Then verify:

```bash
pnpm build
pnpm lint
pnpm test
```

The resulting `pnpm-lock.yaml` must be committed with the manifest changes.

## Why the lockfile is intentionally not hand-edited here

This patch was prepared in an environment without registry access and without pnpm installed. A hand-written lockfile update would risk incorrect dependency resolution or integrity metadata. The clean workflow is therefore to change the source manifests and let the repository's pinned pnpm resolve and write the lockfile on the developer/CI environment.

## Release gate

```text
CAP-003 CI green
    ↓
Deployment hardening
    ↓
pnpm install + lockfile regeneration
    ↓
local build/lint/test
    ↓
GitHub CI
    ↓
Vercel preview
    ↓
Vercel production
    ↓
CAP-003 freeze
```
